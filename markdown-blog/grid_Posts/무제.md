**Grok Bot 현장 매뉴얼: 설정 순서, 스웜 패턴, 그리고 쿼터를 잡아먹는 실수들**  
(Field Manual / rev 1.2 / 2026년 8월 / 40명 이상 운영자 설정 + 공식 문서 + xAI 공개 팁 스레드에서 정리)

대부분의 사람은 Grok Bot을 “추가 단계가 있는 챗봇”처럼 씁니다. 거대한 채팅 하나, 스킬 없음, 스케줄 없음, 수요일쯤이면 쿼터가 다 떨어집니다. 실제로 제대로 결과를 내는 운영자들은 같은 운영 체계로 수렴했습니다. 이 파일이 바로 그 체계입니다. 정신 모델, 설정 순서, 스웜 패턴, 그리고 비싼 교훈을 한 번만 내고 끝내도록 적어 둔 것입니다.

### 1. 정신 모델 (이걸 건너뛰면 계속 막힘)

- **컴퓨터 하나, 화면은 여러 개**: 모든 Bot은 하나의 지속적인 클라우드 컴퓨터(브라우저·파일시스템·터미널이 있는 관리형 Linux VM)를 공유합니다. 각 Bot은 병렬로 작업할 수 있도록 자기 화면을 가지지만, 그 아래에서는 파일, 브라우저 쿠키, 로그인 세션, CLI 자격 증명을 공유합니다. 화면은 작업 공간이지 보안 경계가 아닙니다. 한 사이트에 로그인하면 모든 Bot이 사용할 수 있습니다. 즉, 가장 민감한 로그인에서 한 단계만 떨어져 있습니다. 그에 맞게 신뢰하세요.
- **사다리는 한 칸도 건너뛰지 않음**: 신뢰할 수 있는 경로는 고정되어 있습니다. 일회성 작업 → 수정된 작업 → 저장된 스킬 → 테스트된 루틴 → 팀. 먼저 수동으로 일을 실행하세요. 수정하세요. 그 방법이 실제 접촉을 견뎌낼 때만 스킬로 고정하고 스케줄에 올립니다. 지금까지 읽은 모든 공포 이야기는 누군가 스케줄링을 1번부터 시작해서 생긴 일입니다.
- **Bot은 프로젝트가 아니라 직무**: “일반 도우미”는 아무것에도 이전되지 않는 맥락만 쌓습니다. “Talent Scout”, “Expense Manager”, “Bug Repro”처럼 각 Bot이 몇 달 동안 쌓이는 메모리·파일·선호도를 가져야 합니다. 지속되는 규칙은 Bot 설명에 넣고(“승인 없이 외부 메시지를 보내지 마라”), 작업 세부 사항은 대화에 넣으세요. 설명은 살아남고, 채팅은 스크롤되어 사라집니다.

(그림 1: 모든 Bot 아래에 하나의 VM. 공유 파일, 공유 세션, 공유 자격 증명. 인수인계에는 편리하지만, 읽지 않고 랜덤 스킬을 설치하면 위험.)

### 2. 설정 순서 (대부분 거꾸로 함)

- **먼저 Bot 하나만 만들기: 참모총장(Chief of Staff)**. 다섯 개가 아닙니다. xAI 자체 기업 GTM 플레이북과 일주일 이상 살아남은 모든 설정은 명단을 소유한 단일 조정자로 시작합니다.
- **팀을 역프롬프트로 존재하게 만들기**. 작업, 도구, 반복 업무, 마감일 등 모든 것을 Chief에게 뇌 덤프하세요. 그다음 연결을 검토하고 가장 유용한 전문가·플러그인·자동화 3가지를 제안하게 하세요. 승인하지, 발명하지 마세요. 그다음 한 단계 내려가서 각 새 Bot이 어떤 루틴을 소유해야 하는지 물어보세요.
- **플러그인을 고통 순서로 연결**. Gmail, Calendar, Notion은 원클릭 OAuth입니다. GitHub는 비밀리에 두 경로입니다: Cursor 쪽 링크 + Grok Bot 자체 커넥터(개인 액세스 토큰을 원함). 하나의 녹색 체크가 둘 다 커버하지 않습니다. X는 개발자 베어러 토큰을 원하므로 예산을 10분 잡고 나머지가 작동할 때까지 건너뛰세요.
- **명단을 살 수 있게 만들기**. 상위 2개 Bot을 사이드바 섹션에 고정하고, Bot이 전체 팀에 아바타를 생성하게 하세요. 겉보기엔 화장 같지만, 결국 얼굴이 있는 Bot에게 실제로 메시지를 보내게 됩니다.

### 3. 스킬: 타이핑하지 말고 가르치기

- **“작업 가르치기”가 프롬프트 엔지니어링보다 낫다**. Bot의 컴퓨터 보기를 열고 Teach를 누른 뒤, 일을 한 번 직접 하세요. 마이크 없이 최대 10분의 화면 작업을 녹화하고 스킬 초안을 작성해 줍니다. 한 번의 시연이 버튼 설명하는 저녁을 대체합니다. 프레임 밖으로 비밀을 빼고, 자격 증명은 안전한 인계를 사용하세요.
- **초안은 스킬이 아니다**. 학습된 스킬은 판단 없이 출시됩니다. 사용할 때, 필요한 입력과 접근, 정확한 순서, 검증 방법, 반환할 내용, 승인이 필요한 내용 등 여섯 가지를 명시할 때까지 단단히 하세요. 마지막 줄이 직원과 사고의 차이입니다.
- **스킬은 계정 전체, 활성화는 Bot별**. 저장된 스킬이 / 메뉴에 안 보이면 고장난 게 아닙니다. Settings → Plugins → Yours에서 해당 Bot에 활성화하세요. Composer 문법: /는 스킬 참조, @는 Bot·그룹·루틴·커넥터 멘션.

### 4. 후회 없는 루틴

- **테스트 실행은 실제 작업을 수행한다**. 실제 버튼을 클릭하고, 실제 파일을 바꾸고, 실제 쿼터를 씁니다. 안전한 입력으로 테스트하고 쓰기 작업은 승인 뒤에 두세요. “테스트”는 샌드박스가 아닙니다.
- **아무도 안 읽는 한도**: 계정당 Bot+그룹 채팅 50개, Bot당 루틴 50개, 루틴당 최근 실행 20개만 보관. 루틴 삭제는 되돌릴 수 없고, Bot을 삭제하면 그 루틴도 같이 사라지며, 오래 유휴 상태인 루틴은 답을 줄 때까지 자동 일시정지됩니다.
- **지루한 정책을 앞에 써라**. 소유자, 스케줄, 시간대, 입력 소스, 출력 목적지, 승인 경계. 누락된 데이터에 무엇을 할지(실패 보고, 절대 오래된 데이터 재사용하지 말 것)와 재시도가 멱등적이도록 해서 재실행이 이중 전송이 되지 않게 하세요.
- **자율성은 다이얼이다**. 승인은 fail-once, deny, Always Allow가 될 수 있고, require-approval 규칙이 always-allow보다 낫습니다(둘 다 매치할 때). 전체 Auto Review(Always Allow + Auto Review off)가 존재합니다. 먼저 실행을 지켜보며 얻고, 그다음 워크플로별로 뒤집으세요. 전역으로 하지 마세요.
- **루틴은 스케줄뿐 아니라 이벤트로도 발화한다**. Slack 메시지나 GitHub 알림이 계정 통합을 통해 작업을 시작할 수 있습니다(플러그인 자체와는 별도 연결).

(그림 2: 사다리. 한 칸도 건너뛰지 마라. 수정된 작업을 스킬로 고정하고 루틴과 팀이 무료로 재실행하게 할 때 가치가 복리로 쌓인다.)

### 5. 스웜 패턴 (6개 이상 Bot을 돌리는 사람들로부터)

- **Bot에게 자기 작업을 채점하게 하지 마라**. 신호를 만든 Bot이 최악의 판사입니다. 생산자와 리뷰어를 분리하고, 리뷰어에게 확인 규칙을 주고 인계를 죽이게 하세요. 확신 높은 출력은 두 Bot이 독립적으로 동의해야 합니다.
- **인계는 다섯 가지를 나른다**: 산출물, 증거, 상태, 블로커, 다음 행동. 그 이하면 받는 Bot이 채팅 기록에서 현실을 재구성하고, 그게 드리프트가 시작되는 방식입니다. 단계당 소유자 하나. 그룹 채팅(2~6 Bot)은 인계 자체가 보여야 할 때만.
- **Bot이 가짜로 만들 수 없는 중지 조건**. “완료”는 Bot 자신의 주장이 아닌 다른 것으로 확인 가능해야 합니다: 파일이 URL에 존재, JSON 필드가 임계값을 넘음, PR이 열림. “Bot이 했다고 말한다”를 절대 믿지 마세요.
- **거짓 양성이 지시를 다시 쓰게 하라**. 출력이 약하면 그걸 만든 특정 Bot에게 수정 사항을 메시지하세요(“12개를 플래그했는데 실제 뉴스는 2개였다, 임계값을 높여라”). 30번 반복 후 스웜은 단일 프롬프트가 담을 수 없는 제도적 지식을 보유합니다.
- **스웜에 자체 정체성을 줘라**. AgentMail 유형 플러그인이 Bot이 당신 받은편지함을 태우지 않고 계정에 등록하게 합니다. Tailscale은 기계를 하나의 사설 네트워크로 만들어, 명시적으로 작업을 라우팅할 때 Bot이 도달할 수 있게 합니다.

### 6. 비싼 교훈 (여기서 배우고, 청구서에서 배우지 마라)

- **지속적인 동기화는 쿼터 용광로**. 연결된 서비스를 매일 다시 확인하라고 Bot에게 시키면 배치보다 몇 배 빨리 사용량이 탑니다. 세션 끝에 저장하고 한 번 보고하세요: 주간 보고는 동기화 5번이면 되지 61번이 아닙니다. Grok Bot 한도는 Grok Build와 Cursor와도 별개이므로, 무거운 작업을 셋에 분산해서 하나를 목 조르지 마세요.
- **게시 지연은 정지가 아니다**. “게시해”와 실제 게시 사이에 몇 분이 걸릴 수 있습니다. 명령을 다시 쏘면 이중 게시가 됩니다.
- **LinkedIn은 한번 살아나면 일방통행**. 게시된 글은 이미지를 추가하려고 수정할 수 없습니다. Bot이 첫 댓글로 첨부하게 하세요.
- **막힌 단계만 넘겨받아라**. 로그인이나 2FA 벽이 작업을 멈추면 Agent Computer를 열고 그 한 단계만 한 뒤 계속하라고 말하세요. 비밀번호나 일회용 코드를 채팅에 붙여넣지 마세요. Bot은 그걸 필요로 하지 않고, 대화록이 모든 걸 보관합니다.
- **/workspace만 영원하다**. 그곳 파일과 브라우저 상태는 컴퓨터 업데이트와 복구를 견딥니다. 임시 디렉터리와 직접 설치한 패키지는 일회용입니다. 지속되는 결과는 /workspace나 대화로 가세요.
- **클라우드는 localhost를 볼 수 없다**. Bot은 VM에서 삽니다. 로컬 머신은 정책상 옵트인이고, 로컬 MCP 서버는 도달 불가입니다. 커스텀 커넥터는 호스팅된 HTTP 엔드포인트여야 합니다.
- **실제 부하에서 사용량이 증발한다**. 운영자들은 정직한 멀티 Bot 테스트 2일 만에 7일 체험판을 다 태웠다고 보고합니다. 첫 세션을 돈처럼 계획하세요. 실제로 돈이니까요.

(그림 3: 쿼터 용광로. 출력은 동일하지만 소모량은 다릅니다. 커넥터 동기화를 배치하는 것이 전체 시스템에서 가장 싼 최적화입니다.)

### 7. 리소스 스택 (만들지 말고 훔쳐라)

북마크할 것 (생태계 전체 6개 링크):

- docs.x.ai/grok-bot — 실제 매뉴얼. 스킬·루틴·승인 페이지만으로 일주일 추측을 아낍니다.
- grokbot.dev — 플러그인·사용 사례·컬렉션 봇런 디렉터리. 스케줄로 새 설정을 쿼리할 수 있는 호스팅 MCP 엔드포인트.
- botdirectory.ai — 커뮤니티 프롬프트 디렉터리. 복사 수: Chief of Staff, 계정 트래커, 다이제스트 봇. 당신 것과 멘션 봇을 태그하면 PR 자체가 파일됩니다.
- grokcamp.com — 직무와 플러그인별로 매핑된 45개 현장 테스트 사용 사례. 모든 중요한 행동은 승인 뒤에 유지.
- agensi.io/grok-marketplace — 4,400개 이상 SKILL.md 스킬, 보안 스캔됨, ~/.grok/skills/에 바로 넣기. 같은 파일이 Claude Code, Cursor, Codex에서도 돌아갑니다.
- github.com/xai-org/plugin-marketplace — 공식 플러그인 카탈로그. “지원됨”이 실제로 무엇을 의미하는지 한 저장소에.

**첫 주 체크리스트**

- 1일차: Chief of Staff 만들고 작업을 뇌 덤프, Gmail·Calendar·Notion 연결
- 2일차: Bot 하나에게 지루한 일 하나 주고 수동 실행, 놓친 것 모두 수정
- 3일차: 수정된 방법을 여섯 필드 모두 명시한 스킬로 저장 (다섯 개가 아님)
- 4일차: 안전한 입력으로 테스트 실행 후 시간대와 no-data 정책과 함께 스케줄
- 5일차: Chief가 다음 전문가를 제안하게 하고 하나만 승인 (다섯 개 아님)
- 6일차: 지속 파일을 /workspace로 옮기고 사이드바 섹션 설정, 상위 두 개 고정
- 7일차: 실행 기록 읽고 임계값 하나 조이고 동기화 배치
- 항상: 승인 뒤에 유지하고, 쓰고, 쓰고, 게시하고, 삭제

오늘 밤 부끄러울 정도로 작게 시작하세요. **Bot 하나에게 지루한 일 하나만 주세요.** 세 번 실행하고, 놓친 것을 고치고, 스킬로 고정하고, 스케줄하세요. 일주일 뒤에 그 보고서를 여전히 연다면 유지하고 다음 일을 추가하세요. 그게 전체 시스템입니다.
