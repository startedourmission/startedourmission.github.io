# What Grok Bot actually is

The window looks like a messenger, with names down the left side and bubbles down the right. That is why the first day usually goes the way every other chat has gone: you type a question, you read an answer, you type again.

Behind the bubbles, each name is a teammate with a job, a conversation of its own, and **a working memory that does not get wiped between tasks**.

Every one of them also gets a computer with a browser, a file system and a terminal, and that computer runs in a data center, not on your desk.

Close your laptop halfway through a task and the work keeps going. The FAQ asks "Does Grok Bot keep working when my laptop is closed?" and begins the answer with one word: "Yes."

One account gets one computer, and every employee on it works on its own screen.

Several of them run at the same moment, and because the files, the browser sessions and the logins all live on that one shared computer, whatever one of them finishes and saves is already sitting there for the next one to pick up.

## What deserves its own employee

The first hire is one job. The manual gives five tests, and the job has to clear all five to deserve its own employee:

- **goal:** one area of ownership that belongs to nobody else.
- **sources:** its own set of tools, apps and files.
- **working style:** a way of working that differs from the rest of the roster.
- **approval boundary:** a named line where it stops and asks you.
- **schedule:** the job repeats on a clock.

Talent Scout, Expense Manager and Bug Reproduction clear all five. General Helper clears none: the docs say it gives the bot less guidance and makes its saved context harder to reuse.

Hiring is four moves:

- new chat: **Cmd/Ctrl+N**, or **New** in the sidebar.
- create new agent: choose it there, and a bot called **New Agent** appears.
- **Bot actions** → **Edit Profile**: name, title, description, avatar.
- first message: a real job, never a greeting.

The names people land on are Paul, B1, Stitchy, Dex. Paul Lipsky asked his to pick its own and it came back Atlas.

## The description is the hire

The description is the field people waste. It holds the rules that stay true after you have forgotten writing them.

Today's work goes in the message.

Both role cards in the manual end on a limit. One closes with "Never contact a customer or change an account without approval," the other with "Never change production settings."

Mara is the prospector, and hers is built to that shape:

```markdown
Own weekly prospecting for [what you sell]. Pull names from [sources],
drop anyone already in a sequence, and return a linked list with the
reason each name is on it, strongest first. Never contact anyone
and never buy a list without approval.
```

Four sentences, two of them limits. You can check her work against the description without reading the whole run.

Her first message is today's work, in five fields. Leave one field out and she stops to ask you about it before she starts:

- constraints: what to avoid, and what to ask about first.

**The description you just wrote is also everything the next hire will ever know about Mara.**

**A bot's description is the org chart.**

## Copy the one that already works

Cole works one market and you want a second. Duplicate him:

- carried over: profile, settings, enabled skills, routines and avatar
- not carried over: conversation history, learned memory and chat attachments
- naming: the copy arrives as **\<name> copy**, so rename it before it takes work

The copy lands on the chart with the same job and no history.

Whatever they figure out on the way **dies with the conversation**. Tomorrow morning every one of them starts the job from scratch.

# Step 3 · Teach the job once, then schedule it

Cole's letters this morning had the same two mistakes you fixed on Monday. He kept none of it, so the method still lives in your head.

The docs answer that with an order. Five moves, and the schedule is last:

- run one real task: a live job with a scope that is safe to get wrong
- correct the result: keep going until the output is something you would review
- save the process: the run that worked becomes a named skill
- test it on a second input: a different account, a different file, the same steps
- create the routine: only once retries and failure cases are written down

The schedule only works **because the four moves above it already ran**.

Rina's job is 15 clicks in a browser, so **Teach a task** records it.

The recording runs from the computer view for up to 10 minutes, takes no microphone audio, and hands back the method as a draft you can edit.

Draft is the docs' own word for it. A single recording cannot show what to do when a source goes missing or a price needs approval.

Say this to it, word for word:

```markdown
Save the process we just used as a skill called "Weekly account health." Include the source systems, risk definitions, output format, and the rule that customer contact always requires approval.
```

Sources, rules, output shape and the approval line, fixed in one pass.

**A skill outlives the conversation that taught it.**

A skill still waits to be called. The routine is the call, and one sentence sets the time, the source and the stop rule:

```markdown
Every weekday at 8:00 AM, run the Daily customer-risk skill against the current account list. Post a linked watch list in this conversation. Do not contact customers. If the source data is unavailable, report the failure instead of using old data.
```

That last clause keeps yesterday's numbers out of Monday.

One bot holds up to **50 routines**, and the 20 most recent runs of each stay on record.

The bot runs up to the login and asks. A research bot named Lincoln does exactly that in Paul Lipsky's 11 August walkthrough, stopping for a LinkedIn account.

Five moments need you, and the docs name every one:

- **a password or passkey:** the sign-in itself, once per site
- **two-factor authentication:** the code that lands on your phone

- **a payment or identity check:** money leaving, or proof of who you are
- a site that explicitly requires a human: the rule belongs to the site

Everything outside those five runs without you.

When one lands, open **Agent Computer** from the conversation, take control, do only the blocked step, hand it back, and tell the bot to continue from the current page.

## Use a connector where one exists

Prefer a connector wherever one exists. It is more reliable than clicking through a website, and the browser is there for the sites that never got one.

Adding one takes four moves:

- open **Settings** → **Plugins**
- choose the connector
- press **Add**
- finish the authorization in the browser

Installed connectors are account-wide, so one add covers every bot.

In the message itself, **@** attaches a connector to the task and **/** calls a saved skill.

# The one move that keeps it all alive

Every tool you install goes where tools go, a global install into home. The computer then rebuilds itself on the latest image, and Owen's CLI is not on it any more.

You have more room on that box than anything in the interface lets on. One command, run on a live Grok Bot computer on 14 August:

```python
sudo -n id
# → uid=0(root) gid=0(root) groups=0(root)
```

User **box** carries **(ALL) NOPASSWD: ALL**, so the word between you and root is **sudo**. The docs say the bot starts as a non-root user, and it elevates without a password.

The docs put it softly. Files, browser state and supported sign-ins are "designed to survive normal computer updates and recovery," and you should "treat temporary directories, manually installed packages, and uncommitted application state as replaceable."

The same 14 August check is blunter about it. After an update only **/workspace** was standing: **/home/box/deps** came back empty, apt packages and **/usr** were gone, and Tailscale and ssh had to be installed again more than once.

One folder holds the company. Four subfolders cover everything the roster owns:

- **/workspace/bin**: the CLIs your bots call, with that folder on **PATH**
- **/workspace/config**: every config file those tools read
- **/workspace/skills**: the methods you taught, out of any home directory
- **/workspace/state**: files, results and project state the work produces

Home becomes a cache from there on. Nothing the roster needs rides on an apt package.

The same line goes at the top of every skill, and it is what puts the tools back:

```markdown
Before any other step, run /workspace/bin/bootstrap.sh: install anything missing into /workspace/bin, copy the configs from /workspace/config into place, and put /workspace/bin on PATH. Never install into the home directory and never apt-install into the system.
```

The roster puts its own tools back before it starts working. A missing CLI reinstalls itself and the job continues.

**The roster is only as permanent as the folder it lives in.**
