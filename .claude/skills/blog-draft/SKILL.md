# Blog Draft

> `raw/drafts/`는 없어졌습니다 (2026-08-31). 초안은 **목적지 폴더에 직접** `ready: false` 로 만듭니다 — 목적지는 `python3 tools/ready_queue.py --dest <태그…>` 가 알려줍니다.

이 스킬은 블로그 규칙에 맞는 프론트매터를 자동으로 채워 목적지 폴더에 `ready: false` 초안을 생성합니다.

## 먼저 — 논문 리뷰면 blog-paper-review로 라우팅

사용자 요청이 **논문 리뷰 글의 본문 작성·다듬기·재작성**이면 이 스킬이 아니라 `blog-paper-review` 스킬을 사용합니다. 차이는 다음과 같습니다.

- `blog-draft` — 프론트매터 + **본문 전체 작성**. 정보·잡담 글도 주제가 주어지면 바로 완성도 있는 본문을 씁니다.
- `blog-paper-review` — 조테로 PDF 전문 읽기 + 저자 조사 + Dictionary 항목 생성 + 논문 구조 기반 **본문 한 편 전체 작성**.

다음 신호 중 하나라도 있으면 `blog-paper-review`로 넘깁니다.

- 사용자가 *이 논문 다듬어줘 / 리뷰 써줘 / 다시 써줘*라고 요청
- 이미 `grid_Papers/`에 있는 글의 본문을 **전면 재작성**해야 함
- 결과물에 저자 소개·표·회고가 들어가야 함 (단순 프론트매터 이상)
- 사용자가 기존 글에 *별로다 / 다시 써*라고 품질 부정

`blog-draft`로 처리하는 케이스:
- 논문이 아닌 일반 글 (정보·잡담) — 주제가 주어지면 본문까지 바로 씁니다.

## 왜 이 스킬이 필요한가

새 글을 시작할 때마다 프론트매터 규칙을 다시 떠올리고 옳은 태그·날짜·설명을 채우는 건 마찰이 큽니다. 게다가 잘못된 태그나 형식은 게시 단계에서 막힙니다. 이 스킬이 첫 단추를 정확히 끼워 글쓰기에 곧바로 들어갈 수 있게 합니다.

## 초안 생성 워크플로우

### 1단계 — 정보 수집

**맥락에서 추론할 수 있는 것은 묻지 않습니다.** 사용자가 이미 말한 주제, 말투, 내용으로 판단합니다. 진짜 모호한 경우에만 한 번에 묻습니다.

추론 규칙:

- **제목** — 사용자가 주제를 말하면 바로 제목으로 씁니다. 파일명에 들어가니 `/`, `:`, `?` 같은 특수문자는 피합니다.
- **글 종류** — 맥락으로 판단:
  - 논문·연구 언급 → `논문` (Zotero 연동 가능, 아래 참고)
  - 기술·도구·서비스·이슈 → `정보` (기본값)
  - 개인 의견·경험·가벼운 생각 → `잡담`
  - **글 종류가 맥락에서 명확하면 절대 묻지 않습니다.**
- **주제 태그** (선택, 0~3개) — `LLM`, `머신러닝`, `딥러닝`, `파이썬`, `영상처리`, `데이터분석`, `벤치마크`, `오픈소스`, `AI평가` 중에서 맥락에 맞는 것 자동 선택
- **시리즈** (선택) — `제프리힌턴`, `cs229`, `cme295` 중 해당하면
- **한 줄 설명** — 주제에서 직접 작성합니다. 사용자에게 묻지 않습니다.

**질문을 최소화하는 것이 원칙입니다.** 필요한 정보 대부분은 주제에서 유추할 수 있습니다. 제목, 글 종류, description 모두 합리적으로 추론되면 바로 파일을 만듭니다.

#### Zotero 논문 모드

글 종류가 `논문`이고, 사용자가 Zotero 항목을 언급하거나 논문 제목·DOI를 제시한 경우 Zotero MCP로 메타데이터를 자동으로 가져옵니다.

**트리거 조건** — 다음 중 하나라도 해당하면 Zotero 모드로 진입:
- "조테로에서", "Zotero 논문으로", "이 논문 블로그로" 등 Zotero 명시
- DOI 또는 arXiv ID 제공
- 논문 제목을 직접 언급하며 리뷰 초안 요청

**논문 원문 접근 불가 시 처리 규칙:**

웹 기사·트위터 요약·클리핑만 있고 원문 PDF에 접근할 수 없을 때 — **절대 요약본으로 글을 쓰지 않습니다.** 다음 순서로 처리합니다.

1. WebSearch 등으로 논문 제목과 arXiv/DOI를 먼저 확인합니다.
2. 사용자에게 알립니다: "논문 제목은 **[제목]** 입니다. Zotero에 넣어주시면 전문으로 작성하겠습니다."
3. 사용자가 Zotero에 추가했다고 하면 `mcp__zotero__zotero_get_item_fulltext`로 전문을 가져옵니다.
4. 전문 기반으로 글을 씁니다.

요약본 기반으로 쓴 글은 날짜·기관·실험 수치가 틀릴 수 있습니다. WebFetch가 막히거나 PDF 접근이 실패하면 멈추고 위 절차를 따릅니다.

**Zotero 조회 흐름:**

1. `mcp__zotero__zotero_search_items`로 제목 또는 DOI 검색
2. 결과가 여럿이면 사용자에게 목록 보여주고 선택 받음
3. `mcp__zotero__zotero_get_item_metadata`로 상세 메타데이터 획득
4. (선택) `mcp__zotero__zotero_get_item_fulltext`로 전문 요약 가능 여부 확인

**가져올 메타데이터:**
- 논문 원제 (영문)
- 저자 목록
- 발행 연도, 저널/컨퍼런스명
- DOI / arXiv URL
- 초록 (Abstract)
- Zotero 내 태그·컬렉션 (참고용)

**메타데이터 활용 규칙:**
- 파일명은 **논문 원제(영문) 그대로** 사용. 단, 콜론(`:`)은 ` - `로 대체 (예: `World-R1 - Reinforcing 3D Constraints for Text-to-Video Generation.md`)
- description은 따옴표 없이, 초록을 바탕으로 **2~3문장 도입 문단** 수준으로 작성 (핵심 문제와 접근법을 담음)
- 본문 스켈레톤에 논문 정보 블록 자동 삽입 (아래 템플릿 참고)

### 2단계 — 파일명 결정

파일명은 `markdown-blog/<목적지>/<제목>.md` 형식. 한국어 제목 그대로 둡니다 — 빌드 시스템이 MD5 해시로 URL을 만들기 때문에 한글 파일명도 안전합니다.

같은 이름의 파일이 이미 있으면 사용자에게 알리고 덮어쓸지 다른 이름으로 할지 묻습니다.

### 3단계 — 프론트매터 작성

```yaml
---
date: <오늘 날짜 YYYY-MM-DD>
ready: false
tags:
  - <분류 태그>
  - <주제 태그들>
description: "<한 줄 설명>"
---
```

규칙:

| 항목 | 규칙 |
|------|------|
| `date` | 오늘 날짜로 자동 입력 |
| `ready` | **항상 `false`로 만듭니다.** 게시 승인 체크박스이며 사용자만 켭니다 |
| `tags` | 분류 1개 필수, 총 5개 이하, 따옴표·`#` 금지 |
| `Headliner` | **절대 넣지 않음** — 사용자 권한 |
| `description` | 일반 글: 따옴표 안에 한 줄 / **논문 글: 따옴표 없이 2~3문장 도입 문단** |
| `image` | 본문에 쓸 그림이 있으면 그 파일, 없으면 6단계에서 썸네일을 자동 생성해 채움. 형식은 `image: "![[파일.png]]"` |

#### `ready` — 게시 승인 체크박스

`ready`는 옵시디언 속성 패널에서 체크박스로 뜨는 boolean입니다. 사용자가 초안을 다 읽고 체크하면 그게 게시 승인입니다. 매일 04:00 일일 루틴의 4단계가 `ready: true`인 초안을 전부 게시합니다.

**Claude는 이 값을 절대 `true`로 만들지 않습니다.** 새 초안은 무조건 `ready: false`입니다. Headliner와 같은 성격의 사용자 전용 필드입니다. 사용자가 대화에서 "이거 바로 올려"라고 말하면 `ready`를 켜는 게 아니라 `blog-publish`를 직접 실행합니다.

### 4단계 — 배경 조사 (정보·잡담 글 전부 필수)

#### 레퍼런스 3개 규칙 — 게이트

**정보·잡담 글은 서로 다른 출처 3개 이상을 읽고 씁니다.** 이건 권장이 아니라 진입 조건입니다.

- 출처를 3개 확보하지 못하면 **드래프트를 만들지 않습니다.** 파일을 생성하지 말고 "출처 N개만 확보됨, 3개 미만이라 작성 중단"이라고 사유를 반환합니다. 얇은 글을 만드는 것보다 안 만드는 게 낫습니다.
- **서로 다른 출처**의 기준: 같은 보도자료를 받아쓴 기사 여러 개는 **1개로 셉니다.** 공식 발표문 + 그걸 그대로 옮긴 기사 3개 = 출처 1개입니다.
- 관점이 갈리는 출처를 우선합니다. 공식 발표 / 3자 분석 / 실사용 후기·커뮤니티 반응이 섞이면 좋습니다.
- 논문 리뷰(`blog-paper-review`)에는 이 규칙을 적용하지 않습니다. 논문 원문이 1차 출처입니다.

**출처로 인정되는 것:** 공식 문서·발표, 기술 블로그, 논문, GitHub 저장소·이슈, 벤치마크 결과, 기자·분석가의 독립 분석, HN·커뮤니티의 실사용 보고.

**인정되지 않는 것:** 같은 사건을 다룬 동일 계열 기사 묶음, 원문 없이 인용만 한 요약 글, 우리 블로그의 기존 글.

#### 우라까이 금지

외부 글 한 편을 한국어로 옮기고 순서만 바꾼 글은 만들지 않습니다. 출처 3개를 요구하는 이유가 이것입니다. **3개를 읽되, 3개를 차례로 요약하지 않습니다.** 요약 3개를 이어붙인 글은 우라까이 3편일 뿐입니다.

교차 종합이란 다음을 뜻합니다:

- 출처들이 **공통으로 말하는 것**에서 사실 기반을 세운다.
- 출처들이 **엇갈리는 지점**을 찾아 그 차이가 왜 생기는지 설명한다. 여기가 글의 핵심이 되는 경우가 많습니다.
- 어느 출처도 명시하지 않았지만 **셋을 겹쳐 놓으면 보이는 것**을 짚는다. 이게 우리가 더하는 값입니다.
- 출처마다 무엇을 빠뜨렸는지 본다. 공백도 정보입니다.

한 문단이라도 "A 기사에는 이렇게, B 기사에는 저렇게" 식으로 출처를 나열하는 구조가 되면 다시 씁니다. 본문은 출처가 아니라 **주제**를 따라 전개합니다.

#### 조사 방법

1. `WebSearch`로 최신 뉴스·분석 기사 검색 — 검색어를 바꿔가며 **관점이 다른 출처**를 찾습니다. 같은 결과만 나오면 검색어가 좁은 것입니다.
2. `WebFetch`로 주요 출처 전문 확인 — 제목·요약만 보고 쓰지 않습니다. 3개 모두 본문을 읽습니다.
3. 각 당사자의 **전략적 동기**를 파악 — "왜 이 결정을 내렸는가?"
4. 읽은 출처를 목록으로 정리해두고, 본문 작성 후 **실제로 3개 이상이 본문에 반영됐는지** 확인합니다. 링크만 걸고 내용이 안 들어간 출처는 셈에 넣지 않습니다.

**조사에서 반드시 찾아야 하는 것:**
- 각 당사자가 이 딜/결정에서 얻는 것 (재정적, 전략적, 기술적)
- 표면적 이유 vs 실제 동기 (보도자료 ≠ 진짜 배경)
- 업계 구조상 왜 이런 결정이 나왔는지
- 이 결정이 앞으로 어떤 영향을 미칠지

**조사하지 않고 바로 쓰면 안 되는 것:**
기업 공식 발표를 그대로 요약하는 글은 가치가 없습니다. "A가 B와 계약했습니다. 규모는 X입니다. 변경 사항은 이렇습니다" — 이런 구조는 보도자료와 다를 게 없습니다.

### 5단계 — 본문 작성

주제가 주어지면 **항상 본문까지 바로 씁니다.** 프론트매터만 만들고 멈추지 않습니다. **최대한 풍성하게** 씁니다. 개요만 뽑거나 요점만 나열하지 않습니다. 읽을 가치가 있는 완성도 있는 글을 씁니다.

**풍성하게 쓴다는 것의 기준:**
- 단계별 설명이 필요하면 실제 단계별로 씁니다. "1단계, 2단계..."라고 요약하는 게 아닙니다.
- 외부 링크는 꼼꼼하게 답니다. 공식 문서, GitHub, 관련 글 등 독자가 바로 따라갈 수 있어야 합니다.
- 예시 코드·설정·명령어가 있으면 실제로 씁니다. "예시 코드를 넣으세요" 같은 placeholder 금지.
- 테이블, 코드 블록, 인용구를 적극 씁니다. 텍스트만 가득한 글보다 훨씬 읽기 좋습니다.
- 독자가 "이거 실제로 써볼 수 있겠다"고 느껴야 합니다. 너무 추상적인 설명은 가치가 없습니다.

**뉴스·산업 글에서 인사이트 기준:**
- 각 당사자가 왜 이 판단을 내렸는지 설명합니다. 표면적 이유에 그치지 않습니다.
- 보도자료와 실제 동기가 다를 때 그 간극을 짚어줍니다.
- 업계 구조적 맥락 (경쟁, 기술 병목, 재무 구조) 을 연결합니다.
- 마지막에 이 상황이 앞으로 어디로 가는지 의견을 제시합니다. "~할 것 같습니다", "제 생각에는" — 의견임을 명확히 하되 팩트 기반으로.

**Zotero 논문 모드에서는** 아래 논문 정보 블록을 본문 상단에 자동 삽입합니다:

```markdown
> **원제:** <논문 원제>
> **저자:** <저자 목록>
> **발행:** <연도>, <저널/컨퍼런스>
> **DOI/링크:** <DOI 또는 arXiv URL>

<초록 한국어 요약 1~2문장>

---
```

이 블록 아래에 본문을 이어 씁니다. 구조는 다음을 따릅니다:

- **배경·문제 제기**: H2 없이 본문 바로 시작. 이 연구가 해결하려는 문제를 설명.
- `## 방법론` — 핵심 아이디어와 기술적 접근 (필요 시 H3으로 세분화)
- `## 실험 결과` — 수치와 비교 결과
- `## 결론` — 한계·시사점 포함 (❌ `## 한계와 시사점`으로 쓰지 않음)

- **존댓말 기반 스토리텔링** — 딱딱한 보고서 톤 X
- **흐름:** 문제 제기 → 해결 방법 → 사용 예시 → 시사점
- **H2 5~7개 이내**
- **본문에 H1 사용 금지** (빌드가 제목으로 자동 생성)
- **검증되지 않은 수치 금지** — 출처 없는 "30% 향상" 같은 표현 X
- **위키 링크 적극 사용** — `[[항목명]]` 형식

### 6단계 — 썸네일 생성 (이미지 없을 때만)

게시된 글은 `image` 필드를 카드·OG 썸네일로 씁니다. 비어 있으면 빌드가 기본 아바타(notion_avatar.png)로 폴백해서 글마다 똑같은 그림이 붙습니다. 그래서 초안 단계에서 미리 채워둡니다. (예전에는 이걸 blog-publish의 게시 단계로 미뤘는데, 초안에서 만들어 두면 작성자가 Obsidian에서 바로 확인할 수 있습니다.)

판단은 간단합니다.

1. **본문에 글 내용을 보여주는 그림이 있으면 그 파일을 `image`로 씁니다.** 제품 스크린샷·다이어그램·로고처럼 본문에 이미 넣은 이미지가 있거나 사용자가 이미지를 지정했다면, 그걸 가리키고 새로 만들지 않습니다.
2. **그림이 없으면 썸네일 생성을 Codex 서브에이전트에 위임합니다.** 직접 만들지 말고 Codex에 넘기세요 — 디자인·이미지 생성은 Codex 쪽이 더 잘 처리합니다. 정보·잡담 글은 대개 figure가 없어 이 경로로 옵니다.

먼저 저장 위치를 정합니다. 이미지는 **글이 게시될 폴더의 `_assets/`** 에 둬야 빌드에서 404가 나지 않습니다(크로스 폴더 참조 금지). 목적지는 글 종류로 정하며, blog-publish가 쓰는 규칙과 같습니다.

| 글 종류 | 목적지 `_assets/` |
|---------|------------------|
| 정보·잡담 | `markdown-blog/grid_Posts/_assets/` |
| 논문(Zotero 모드) | `markdown-blog/grid_Papers/_assets/` |
| 제프리힌턴 시리즈 | `markdown-blog/Geoffrey Hinton/_assets/` |
| cs229 시리즈 | `markdown-blog/CS229 Lectures/_assets/` |
| cme295 시리즈 | `markdown-blog/CME295 Lectures/_assets/` |

**위임 방법:** `Agent` 도구를 `subagent_type: "codex:codex-rescue"`로 호출하고, 프롬프트에 다음을 담습니다. (이건 blog-publish가 쓰던 위임 방식과 같습니다 — 이제 그 단계를 초안 쪽으로 앞당긴 것뿐입니다.)

- 글 제목, 분류 태그, 한 줄 description
- 목적지 폴더 경로 (예: `markdown-blog/grid_Posts/`)
- 썸네일 저장 경로: `<목적지>/_assets/<제목>-thumb.png`
- 스타일 가이드: 검은 선 + 흰 배경, 미니멀, 텍스트는 영문, 1200×630 (OG 이미지 비율)
- 작업 완료 후 생성된 파일의 절대경로를 반환하라고 명시

Codex가 만든 파일이 실제로 존재하는지 확인한 뒤, 프론트매터에 `image: "![[<제목>-thumb.png]]"`를 넣습니다. **파일명만** 넣고 경로는 적지 않습니다 — Obsidian과 빌드가 `_assets/`에서 알아서 찾습니다.

초안 md는 목적지 폴더에 있어도 이미지는 목적지 `_assets/`에 두는 게 맞습니다. blog-paper-review도 같은 방식이고, blog-publish는 이미 목적지에 있는 이미지를 인식해 동반 이동을 건너뜁니다. Obsidian은 볼트 전역에서 `![[파일]]`을 찾으므로 초안을 열어도 썸네일이 바로 보입니다.

사용자가 "썸네일 없이"라고 하면 이 단계를 건너뜁니다(빌드가 기본 아바타로 폴백).

### 7단계 — 파일 생성 및 안내

파일을 쓴 뒤 경로를 알려주고, 사용자가 본문을 이어쓸 수 있게 합니다. 썸네일을 만들었으면 그 경로도 함께 알립니다. 게시 준비가 되면 `blog-publish` 스킬로 넘어갈 수 있다고 알립니다.

## 예시

**사용자:** "DeepSeek V4 출시 임박이라는 제목으로 정보 글 초안 만들어줘. LLM 관련."

스킬은:
1. 제목: `DeepSeek V4 출시 임박`, 분류: `정보`, 주제: `LLM`
2. description을 주제에서 추론해 바로 씁니다. 묻지 않습니다.
3. WebSearch로 최신 DeepSeek V4 소식 조사
4. `markdown-blog/<목적지>/DeepSeek V4 출시 임박.md` 생성 — 프론트매터 + 본문 전체:

```yaml
---
date: 2026-04-25
ready: false
tags:
  - 정보
  - LLM
description: "DeepSeek V4의 예상 출시 시점과 주요 변경점을 정리합니다"
---

(본문 전체 작성)
```

4. 게시 준비가 되면 `blog-publish`로 올릴 수 있다고 안내.

## 라이팅 스타일 (startedourmission)

모든 본문은 이 스타일을 따릅니다.

### 먼저 — 정보·잡담 글은 STYLE.md를 우선 적용

본문을 쓰기 전에 볼트 루트 `STYLE.md`를 읽고 그 규칙을 적용합니다. 특히 정보·잡담 글에서 다음 셋은 내 기본값이 자꾸 흘러가는 곳이라 의식적으로 **뺍니다.**

1. **자기 감상·메타코멘트 금지** — "저도 써봤는데", "인상적입니다", "재밌습니다", "와닿습니다", "흥미롭습니다" 류. 무엇을 느꼈는지가 아니라 개념이 무엇인지를 씁니다.
2. **카피성 제목·소제목 금지** — 제목은 자극적 카피 말고 다루는 개념으로. H2는 부제·콜론 붙은 긴 문장 말고 짧은 명사형으로 (`## 다섯 프롬프트`, `## 저지`).
3. **강박적 비판·출처 의심 단락 금지** — "균형 맞추려" 별도 "제 생각" 섹션이나 본문 중간 출처 의심("이 수치는 그대로 믿기보다")을 끼우지 않습니다. 비판은 마지막에 짧은 동의/의견 한 문단으로 갈음. (팩트 교정은 당연히 함.)

**출처는 글 끝에 목록으로 모읍니다.** 맨 아래 `---` 아래에 `참고:` 한 줄로 읽은 출처 3개 이상을 링크로 나열합니다. 본문 중간에 "A 매체에 따르면", "글쓴이는~"을 반복하지 않습니다. 본문은 출처를 소개하는 곳이 아니라 종합한 결과를 전달하는 곳입니다.

수치나 인용처럼 **어느 출처인지 밝혀야 신뢰가 서는 대목**에서만 본문에 링크를 겁니다. 그 외에는 끝의 목록으로 갈음합니다.

예외 — 한 편의 글을 정면으로 다루는 리뷰·반박 성격의 글이면 맨 위 인용구 1줄(`> 이 글은 [출처](URL)를 참고하여 작성했습니다.`)을 씁니다. 이때도 배경 출처 2개 이상을 추가로 읽고 끝의 목록에 넣습니다.

아래 상세 스타일은 위 우선 규칙과 충돌하면 STYLE.md / 위 블록이 이깁니다. (예: "겸손한 자신감"의 "~것 같습니다"는 감상 과잉으로 흐르기 쉬우니 정보 글에서는 절제.)

### 톤 & 보이스

- **친근한 전문성**: 격식 없지만 존중하는 톤. "~입니다", "~네요", "~죠"
- **이모지 절대 금지**: 대신 구어체 감탄사. "오~", "아!", "최고~", ",,"
- **겸손한 자신감**: "제 생각에는", "~것 같습니다", "~구나 싶네요"
- **비판은 맥락 고려**: 팩트 기반 지적 + 대안 또는 균형잡힌 시각
- 과장 표현 금지: "놀라운", "혁신적인", "획기적인", "세계 최초" ❌

### 문장 구조

- 짧고 명확한 문장. 한 문장 = 한 아이디어.
- 단락은 2~3문장 단위로 명확히 구분.
- 능동태 우선. 복잡한 종속절 중첩 금지.

### 정보 전달 순서

1. 핵심 결론/요약 먼저
2. 배경 설명
3. 상세 분석
4. 개인 의견/비판적 고찰

### 깊이 기준 (중요)

기술·논문 주제는 **거의 논문을 번역하다시피** 깊게 씁니다.

- 개념 → 메커니즘 → 구체적 예시 → 수치 → 한계 순서로 전개
- "왜 이게 중요한가?"를 항상 설명
- 추상 개념은 반드시 구체 예시와 함께
- 관련 시스템·구현체 실명으로 비교
- 수식이 필요하면 라텍스 사용 후 문장으로 설명
- 요점만 나열하는 글은 가치 없음. 독자가 메커니즘을 이해해야 함

### 비판 원칙

- 팩트 기반, 맥락 고려, 대안 제시
- 문서 성격 파악 후 평가 (기술 보고서 ≠ 학술 논문)
- "이 부분은 아쉽습니다" vs "이건 잘못됐습니다" 구분
- 긍정만 쓰지 않음. 한계와 의문도 포함

### 완성 체크리스트

- [ ] **서로 다른 출처 3개 이상을 읽고 본문에 반영했음** (정보·잡담 글 필수, 미달이면 드래프트 생성 자체를 중단)
- [ ] **출처를 차례로 요약한 구조가 아님** — 주제를 따라 전개되고, 출처가 엇갈리는 지점이나 겹쳐야 보이는 것을 최소 한 대목 이상 짚었음
- [ ] 글 끝에 `참고:` 출처 목록 있음
- [ ] 이모지 없음
- [ ] 과장 표현 없음
- [ ] 팩트와 의견 구분
- [ ] 구체적 예시 포함
- [ ] 비판적 시각 포함 (맥락 고려)
- [ ] 단락 명확히 구분
- [ ] 전문 용어 설명 충분
- [ ] 억까 아닌 합리적 비판
- [ ] Dictionary 항목 있는 용어 `[[위키링크]]` 연결 완료
- [ ] 중요 신규 용어가 있으면 Dictionary 항목 먼저 생성했음

## 하면 안 되는 것 — 구체적 금지 패턴

### ❌ 본문에 H1 넣기 — 절대 금지

빌드 시스템이 파일명에서 제목을 자동 생성합니다. H1이 본문에 있으면 제목이 두 번 나옵니다.

나쁜 예:
```
---
tags:
  - 정보
---

# Claude vs GPT 비교   ← 이거 절대 금지
```

올바른 예:
```
---
tags:
  - 정보
---

Claude와 GPT, 둘 다 LLM인데 왜 따로 쓰는 걸까요.  ← H2부터 시작하거나 바로 본문
```

### ❌ 스펙시트·나열 구조 — 금지

테이블과 리스트로만 채운 글은 가치가 없습니다. 독자가 메커니즘을 이해해야 합니다.

나쁜 예 (이런 글 쓰지 마세요):
```
## 핵심 스펙 비교
| 항목 | Claude | GPT |
|------|--------|-----|
| 컨텍스트 | 200K | 1M |

## 장단점
**Claude 장점:**
- 긴 문서 처리
- 안전 철학
```

올바른 예:
```
## 컨텍스트 창: 숫자보다 실제 쓰임이 중요합니다

Claude는 200K 토큰, GPT-5.4는 1M 토큰입니다. 숫자만 보면 GPT가 5배 유리합니다.
그런데 실제로는 조금 다릅니다. Liu et al.의 "Lost in the Middle" 연구에서 밝혔듯,
LLM은 긴 컨텍스트의 중간을 체계적으로 무시합니다.
200K를 꽉 채운 Claude가 1M 중 앞뒤만 보는 GPT보다 실제 품질이 나을 수 있습니다.
```

### ❌ 개요·placeholder 작성 — 금지

"이 섹션에서는 X를 다룹니다", "[여기에 상세 설명 추가]" 같은 메타 서술 절대 금지.
실제 메커니즘을 바로 설명합니다. "설명합니다"가 아니라 설명 자체를 씁니다.

### ❌ Headliner 태그 임의 추가 — 절대 금지

아무리 잘 쓴 글이어도 Headliner는 사용자가 직접 추가합니다. Claude가 판단하지 않습니다.

### ❌ 이모지 사용 — 금지

섹션 제목, 본문, description 어디에도 이모지 없습니다.

나쁜 예: `## 🚀 Claude의 강점`
올바른 예: `## Claude가 실제로 잘 하는 것`

### ❌ 과장·마케팅 언어 — 금지

"놀라운", "혁신적인", "게임체인저", "획기적인", "세계 최초" 등 검증 불가 수식어 사용 금지.

### ❌ 위키링크 없이 인물·개념 언급

Dictionary(`markdown-blog/Dictionary/`)에 항목이 있는 **모든 용어**는 첫 등장 시 반드시 `[[항목명]]`으로 연결합니다. 인물, 모델, 벤치마크, AI 개념, 기업, 칩, 도구 모두 포함합니다.

나쁜 예: `Andrej Karpathy는 바이브 코딩이라는 용어를 만들었습니다.`
올바른 예: `[[Andrej Karpathy]]는 바이브 코딩이라는 용어를 만들었습니다.`

파일명과 표시 텍스트가 다를 때는 pipe 형식으로: `[[Amazon Trainium3|Trainium]]`, `[[Google TPU v7 Ironwood|Ironwood TPU]]`

**Dictionary에 없지만 중요한 개념이 본문에 등장하면** — Dictionary 항목을 먼저 만들고 나서 링크합니다.

Dictionary 항목 생성 기준:
- AI 모델·칩·도구·플랫폼 (예: MCP, 새로운 GPU 아키텍처)
- 핵심 ML/AI 기법 (예: 증류, 새 학습 알고리즘)
- 주요 인물·기업

항목 생성 시 프론트매터 필수 필드: `date`, `tags`, `description`

**인물 항목(`type: person`)은 파일명을 한글 이름으로 짓고**(2026-07 규칙 — 중국계는 병음을 성 먼저 음차해 붙여씀 `왕리민`·`허카이밍`, 서양은 표준 한글 음차 `크리스 래트너`, 한국계는 실제 한글명 `이병관`; `페이-페이 리`처럼 given-first로 굳은 경우만 그 순서), 영문·한자 이름은 `aliases`에 넣는다. **새로 만들기 전에 같은 사람이 다른 표기로 이미 있는지 파일명·aliases를 확인**해 중복 노트를 막는다. star 점수 계산을 위한 추가 필드:

```yaml
aliases:
  - <영문 이름>          ← 파일명은 한글, 영문은 alias로
  - <한자 (있으면)>
tags:
  - 인물
  - <도메인 태그>
  - <해당 점수 태그들>   ← 아래 목록에서 골라 추가
last_active: <YYYY>     ← 마지막 논문·발표·직책 활동 연도
papers:                 ← 저자로 참여한 블로그 게시 논문 (파일명, .md 제외)
  - Attention Is All You Need
```
