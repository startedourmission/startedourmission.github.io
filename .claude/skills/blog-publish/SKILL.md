# Blog Publish

> `raw/drafts/`는 없어졌습니다 (2026-08-31). 초안은 **목적지 폴더에 직접** `ready: false` 로 만듭니다 — 목적지는 `python3 tools/ready_queue.py --dest <태그…>` 가 알려줍니다.

이 스킬은 목적지 폴더의 초안을 검증하고 적절한 `markdown-blog/` 하위 폴더로 옮긴 뒤 git push까지 수행합니다.

## 왜 이 스킬이 필요한가

이 블로그는 옵시디언에서 마크다운으로 쓰고 F# 빌드 시스템이 HTML로 변환해 GitHub Pages에 배포하는 구조입니다. 게시 단계마다 사람이 신경써야 할 디테일이 많습니다 — 프론트매터 검증, 본문 사실 검증, 태그 기반 폴더 결정, git 작업. 이 스킬이 이 워크플로우를 한 번에 처리해 사용자가 글 자체에만 집중할 수 있게 합니다.

## 경로 상수

스킬 안에서 아래 경로를 씁니다. 셸에서 먼저 정의하세요.

```bash
VAULT="$HOME/Vaults/AutoVault"
POSTS="$VAULT/markdown-blog"
CLIPPINGS="$VAULT/Clippings"
```

## 게시 큐 — `ready` 체크박스

초안 프론트매터의 `ready`는 옵시디언 속성 패널에서 체크박스로 뜨는 boolean입니다. 사용자가 초안을 다 읽고 체크하면 그게 게시 결재입니다. 매일 04:00 일일 루틴의 마지막 단계가 체크된 초안을 **전부** 게시합니다.

- **Claude는 `ready`를 켜지 않습니다.** `Headliner`와 같은 사용자 전용 필드입니다. 대화에서 "이거 올려줘"라고 하면 체크박스를 켜는 게 아니라 이 스킬을 바로 실행합니다.
- 큐 조회·해제는 `tools/ready_queue.py`가 담당합니다. LLM이 grep으로 훑지 않습니다.
- **`ready: true` 는 게시본에 그대로 남습니다.** 영구 필드입니다 (2026-08-31 이후). 빌드는 `ready: false` 만 걸러냅니다 — 필드가 없거나 true 면 게시됩니다.

### 헤드리스 배치 실행 규칙

크론이 큐를 통째로 넘길 때는 아래를 지킵니다.

- **한 편이 막혀도 멈추지 않습니다.** 실패한 초안은 건너뛰고 다음으로 넘어갑니다. 큐 하나가 전체 루틴을 세우면 안 됩니다.
- **막힌 초안은 `ready: true`인 채로 목적지 폴더에 그대로 둡니다.** 사용자가 고치면 다음 날 자동으로 재시도됩니다. 실패했다고 체크를 해제하지 않습니다.
- **차단 사유는 반드시 로그에 남깁니다** — 파일명, 어느 게이트에서 막혔는지, 구체적 오류. 사용자가 로그만 보고 고칠 수 있어야 합니다.
- 게시 성공분과 차단분을 나눠 요약합니다.

차단 사유별 처리:

| 상황 | 처리 |
|------|------|
| `validate.py` invalid (2단계) | 건너뜀. 오류 목록 로그에 기록 |
| 팩트체크 ❌ 모순 (3단계) | 건너뜀. 어긋난 문장·올바른 값 로그에 기록. **헤드리스에서 본문을 임의로 고쳐 게시하지 않습니다** |
| 팩트체크 ⚠️ 검증 불가 | 차단하지 않고 게시. ⚠️ 목록만 로그에 기록 |
| 목적지 폴더 확정 불가 (`dest: null`) | 건너뜀. 태그 조합을 로그에 기록하고 사용자 판단을 기다림 |
| 썸네일 없음 (6단계) | Codex 위임을 시도하되, 실패하면 기본 아바타 폴백으로 그대로 게시. 이걸로 차단하지 않음 |
| RSS invalid (8단계) | **push 차단.** 이미 옮긴 파일을 목적지 폴더로 되돌리고 로그에 `line:col`·codepoint 기록 |
| git push 실패 | 초안 삭제(10단계)를 하지 않습니다. 다음 실행에서 재시도됩니다 |

**발행량 상한은 이 경로에 적용하지 않습니다.** CLAUDE.md의 "하루 논문 1편 + 정보·잡담 1편"은 수집·작성 트랙 규칙입니다. 게시 트랙은 별개이고, 체크된 큐는 사용자가 이미 편당 검토를 마친 것이므로 몇 편이 체크돼 있든 그날 전부 올립니다.

## 게시 워크플로우

### 1단계 — 대상 파일 확인

사용자가 파일명을 지정했으면 목적지 폴더에서 해당 파일을 찾습니다. 한국어·영문 파일명이 섞여 있고 논문글은 긴 영문 원제를 쓰므로 부분 일치(예: "SkillOrchestra"만 말해도 `SkillOrchestra - Learning to Route Agents via Skill Transfer.md`를 찾음)로 매칭하세요.

지정하지 않았으면 목적지 폴더의 마크다운 목록을 보여주고 어떤 글을 게시할지 물어봅니다.

**헤드리스(크론) 호출이면 대상을 게시 큐에서 받습니다.** 목록을 눈으로 훑지 말고 아래를 실행하세요.

```bash
python3 "$VAULT/tools/ready_queue.py"
```

`ready: true`로 체크된 초안만 JSON으로 나옵니다. 오래된 `date` 순으로 정렬돼 있으니 그 순서대로 처리합니다. `count: 0`이면 게시할 게 없다는 뜻이므로 아무것도 하지 않고 그 사실만 보고합니다.

### 2단계 — 프론트매터 검증 (구조 게이트, 자동)

**먼저 `tools/validate.py`를 실행합니다.** Claude가 눈으로 확인하는 대신 결정론적 Python이 구조 게이트를 지킵니다.

```bash
python3 "$VAULT/tools/validate.py" "$DRAFTS/<파일명>.md"
```

`status: "invalid"`가 나오면 오류 목록을 사용자에게 보여주고 수정 방안을 제시합니다. 수정 후 재검증이 통과될 때까지 다음 단계로 진행하지 않습니다.

검증 항목:

| 항목 | 규칙 |
|------|------|
| `date` | `YYYY-MM-DD` 형식 |
| `tags` | 분류 태그 1개 필수(`논문`/`정보`/`잡담`), 5개 이하, 따옴표·`#` 없음 |
| `description` | 한 줄 설명 존재 |
| 본문 H1 | `# 제목` 줄이 본문에 없어야 함 (빌드가 자동 생성) |
| XML 제어문자 | 보이지 않는 제어문자(U+0008 등) 없어야 함 (RSS 피드 깨짐 방지) |

**이 제어문자 검사가 RSS 방어 게이트 1입니다.** 빌드가 제목·description·본문을 전부 CDATA로 감싸므로, 피드를 깨뜨릴 수 있는 유일한 것은 XML 1.0 불법 제어문자(U+0000-001F 중 tab/LF/CR 제외, U+FFFE/FFFF)입니다. LaTeX 백슬래시나 코드스팬 `<...>`은 CDATA 안이라 피드를 깨지 않습니다(과거 이걸 원인으로 지목한 게 오답이었던 이유). `validate.py`가 파일명(=RSS 제목 소스)과 본문 전체를 스캔해 이걸 즉시 잡습니다. 게이트 2(실제 생성물 검증)는 아래 8단계에 있습니다.

`status: "valid"` 확인 후에만 계속 진행합니다.

추가로 Claude가 직접 확인하는 것:
- `Headliner` 태그 — **사용자가 직접 넣지 않은 한 절대 추가하지 않음** (유일한 예외: 7.5단계의 이달의 인물 자동 교체)
- 이미지 참조 — `![[파일.png]]` 형식, 다른 폴더 이미지 참조 금지
- `date` 갱신 — 오늘 날짜와 다르면 갱신 제안
- 부가 필드 보존 — 논문글에 흔한 `aliases`, `citations`, `buzz`는 건드리지 않고 그대로 둡니다. 검증기는 이 필드들을 무시하므로 통과에 영향 없습니다.
- 빈 이미지 — `image: "![[]]"`처럼 참조가 비어 있으면 "썸네일 없음"으로 취급합니다(6단계 대상).

문제가 있으면 어떻게 고칠지 사용자에게 보여주고 동의를 받은 뒤 수정합니다.

### 3단계 — 팩트체크 (내용 게이트)

`validate.py`는 구조만 봅니다. 본문의 사실 주장이 맞는지는 검증하지 않습니다. 본문 작성 단계에서 이미 검토했더라도, 게시 직전 **독립적으로 한 번 더 전수 검증**합니다 — 작성 중 놓친 것, 이후 수정으로 새로 들어온 오류를 게시 전에 잡기 위함입니다.

이 단계는 판단이 필요하므로 Python 게이트가 아니라 Claude가 직접 수행합니다. `WebSearch`/`WebFetch`, 논문글이면 Zotero 풀텍스트(`zotero_get_item_fulltext`) 도구를 씁니다(모두 지연 로드 — 먼저 `ToolSearch`로 스키마를 불러오세요).

**절차:**

1. **소스 확보.**
   - **논문글**(`논문` 태그, `grid_Papers/`): 원문 arXiv/PDF를 진실의 기준으로 삼습니다. 프론트매터·본문의 arXiv 링크, 또는 Zotero 풀텍스트에서 확보합니다. (Zotero 스토리지가 꽉 차 PDF 첨부가 안 되면 arXiv에서 직접 받는 우회를 씁니다.)
   - **정보·잡담글**: 본문 상단 인용구 `> 이 글은 [출처](URL)`의 URL, 또는 본문 내 링크를 `WebFetch`로 가져옵니다.
   - 선언된 소스가 없으면(순수 오리지널 글) 웹 검색으로만 대조합니다.

2. **검증 대상 주장 전수 추출.** 본문을 훑어 검증 가능한 사실 주장을 **모두** 뽑습니다:
   - 수치·지표 — 정확도, %p, 배수, 파라미터 수, 벤치마크 점수, 가격, 날짜, 버전
   - 고유명사 — 저자, 소속 기관, 회사, 모델명, 제품명, 논문 제목
   - 정량 비교·최상급 — "X가 Y보다 22.5%p 높다", "700배 저렴", "최초/최고/유일"
   - 인용·귀속 — "저자에 따르면", "논문은 ~라 주장"
   - 기술적 사실 — 아키텍처, 방법론, 데이터셋 규모

3. **각 주장 대조.** 소스(원문) 우선, 없으면 웹으로 대조해 분류합니다:
   - ✅ 확인됨 — 소스/웹과 일치
   - ⚠️ 검증 불가 — 소스에 없고 웹으로도 확정 못 함
   - ❌ 모순 — 소스/웹과 어긋남 (틀린 수치, 잘못된 기관·저자, 존재하지 않는 사실)

4. **게이트 판정.**
   - **❌가 하나라도 있으면 게시를 차단합니다.** 어긋난 문장·올바른 값·근거(소스 위치나 검색 결과)를 사용자에게 보여주고 수정안을 제시합니다. 수정 후 재검증이 통과할 때까지 다음 단계로 넘어가지 않습니다.
   - **⚠️는 차단하지 않되** 목록으로 사용자에게 보고합니다("이 수치는 소스에서 확인하지 못했습니다"). 사용자가 유지/수정/삭제를 결정합니다.
   - 전부 ✅면 통과합니다.

5. 결과는 5단계(사용자 확인 게이트)에서 요약 표로 함께 보여줍니다.

**주의 — 교정은 값을 고치는 것이지 의심 문장을 본문에 넣는 게 아닙니다.** `STYLE.md`가 "출처 의심 단락"을 금지합니다. 틀린 수치는 올바른 값으로 바꾸되, "이 수치는 불확실하다" 같은 헤지 문장을 본문에 끼워넣지 않습니다. 교정은 항상 사용자 동의를 받고 반영합니다.

### 4단계 — 위치 검증

글은 **이미 목적지 폴더에 있습니다** (생성 시점에 결정됨). 여기서는 태그와 실제 위치가 맞는지만 확인하고, 어긋나면 옮깁니다. `python3 tools/ready_queue.py --dest <태그…>` 가 정답 폴더를 알려줍니다.

| 태그 | 목적지 |
|------|--------|
| `논문` | `markdown-blog/grid_Papers/` |
| `정보` 또는 `잡담` | `markdown-blog/grid_Posts/` |
| `KMS` | `markdown-blog/Knowledge Management System/` |
| `제프리힌턴` | `markdown-blog/Mastermind/Geoffrey Hinton/` |
| `얀르쿤` | `markdown-blog/Mastermind/Yann LeCun/` |
| `cs229` | `markdown-blog/Lectures Translate/CS229 Lectures/` |
| `cs230` | `markdown-blog/Lectures Translate/CS230 Lectures/` |
| `cme295` | `markdown-blog/Lectures Translate/CME295 Lectures/` |
| `파이썬` 코스 | `markdown-blog/Course/Python/` |
| 사전·인물·벤치마크 | `markdown-blog/Dictionary/` |

**예외:** 시리즈·코스 태그(제프리힌턴/얀르쿤/cs229/cs230/cme295/KMS/파이썬 코스)가 있으면 분류 태그보다 시리즈 폴더를 우선합니다. 예를 들어 `정보 + KMS`라면 `Knowledge Management System/`로 갑니다.

**애매하면 확정하지 말고 물어봅니다.** 표에 없는 조합이거나 `Course/AI 시작하기`처럼 수작업으로 큐레이션되는 폴더가 목적지 후보로 보이면, 임의로 경로를 정하지 말고 사용자에게 확인합니다.

결정된 경로를 사용자에게 알립니다.

### 5단계 — 사용자 확인 (필수 게이트)

**여기서 반드시 멈춥니다.** 파일은 아직 목적지 폴더에 있어야 합니다. 이동·push는 사용자 확인 전에 절대 하지 않습니다.

사용자에게 다음을 보여주고 게시 의사를 확인합니다:
- 대상 파일 경로 (`markdown-blog/<목적지>/<파일명>.md`)
- 이동될 경로
- **팩트체크 요약** — ✅/⚠️ 개수, ⚠️ 항목 목록 (❌가 있었다면 3단계에서 이미 차단·교정됨)
- 예정 커밋 메시지

사용자가 명시적으로 "올려", "push", "ㅇㅇ", "응" 등 게시 의사를 밝혀야만 6단계로 넘어갑니다.

**헤드리스(크론)에서는 `ready: true`가 이 게이트를 대신합니다.** 사용자가 옵시디언에서 체크박스를 켠 것이 게시 결재이기 때문입니다. 물어볼 사람이 없으므로 `AskUserQuestion`을 호출하지 말고 바로 6단계로 넘어갑니다. **대신 2·3·8단계의 자동 게이트는 그대로 지킵니다** — 체크박스는 "읽어봤고 올려도 된다"는 뜻이지 "검증을 건너뛰라"는 뜻이 아닙니다.

### 6단계 — 썸네일 생성 (Codex 위임, 사용자 확인 후 실행)

프론트매터에 `image:` 필드가 없거나 비어 있으면(`image: "![[]]"` 포함), Codex 서브에이전트에 썸네일 생성을 위임합니다. 직접 만들지 말고 무조건 Codex에 넘기세요 — 디자인·이미지 생성은 Codex 쪽이 더 잘 처리합니다.

**위임 방법:** `Agent` 도구를 `subagent_type: "codex:codex-rescue"`로 호출. 프롬프트에 다음을 포함합니다:

- 글 제목, 분류 태그, 한 줄 description
- 목적지 폴더 경로 (예: `markdown-blog/grid_Posts/`)
- 썸네일 저장 경로: `<목적지>/_assets/<제목 슬러그>.png`
- 스타일 가이드: 검은 선 + 흰 배경, 미니멀, 텍스트는 영문, 1200×630 권장 (OG 이미지 비율)
- 작업 완료 후 생성된 파일의 절대경로를 반환하라고 명시

Codex가 생성한 파일이 실제로 존재하는지 확인한 뒤, 마크다운 프론트매터의 `image:` 필드를 `image: "![[<파일명>.png]]"` 형식으로 채웁니다.

이미 `image:` 필드가 채워져 있으면(요즘은 보통 blog-draft가 초안 단계에서 채워 둡니다) 새로 만들지 않습니다. 대신 `image:`가 가리키는 파일과 본문의 `![[파일.png]]` 이미지를 점검합니다.

- **이미 목적지 `_assets/`에 있으면 그대로 둡니다** — blog-draft가 만든 썸네일이 여기 해당합니다. 이동도 재생성도 하지 않습니다.
- 목적지에 없고 볼트 다른 위치에 있으면 찾아서 목적지 `_assets/`로 동반 이동합니다.
- 어디에서도 못 찾는 참조만 게시를 중단하고 사용자에게 알립니다 — 빌드 시 404가 나기 때문입니다.

사용자가 "썸네일 없이 그대로 올려"라고 명시하면 이 단계를 건너뜁니다 — 빌드가 기본 아바타(notion_avatar.png)로 fallback합니다.

### 7단계 — (삭제됨)

파일 이동과 `ready` 제거는 2026-08-31 구조 변경으로 없어졌습니다. 글은 처음부터 목적지에 있고, `ready` 는 남깁니다. 4단계에서 위치가 맞는지만 확인하면 됩니다.

### 7.5단계 — 이달의 인물 Headliner 자동 교체 (유일한 예외)

**Headliner는 원칙적으로 사용자 전용 필드입니다 (CLAUDE.md).** 단 하나, 파일명이 `YYYY. MM. 이달의 인물 - ...` 패턴과 일치하는 글에 한해 2026-08 사용자 지시로 다음을 자동 수행합니다. 다른 어떤 글에도 이 예외를 확장하지 않습니다.

1. 이달의 인물 글의 프론트매터 `tags`에 `Headliner`를 추가합니다.
2. `markdown-blog/grid_Posts/`에서 같은 패턴의 다른 이달의 인물 글을 전부 찾아, `Headliner` 태그가 있으면 제거합니다(보통 바로 이전 달 글 하나).
3. 이 두 변경은 9단계에서 같은 커밋에 함께 넣습니다.

이 글이 아니면(태그가 `잡담`이어도 파일명이 이 패턴이 아니면) 이 단계를 건너뜁니다.

### 8단계 — RSS 검증 (소스 스캔, 빌드 없음)

**메모리 교훈: RSS 오류는 소스를 눈으로 추측해서 잡지 않는다.** 과거 LaTeX·코드스팬을 원인으로
지목한 "해결"이 두 번 다 오답이었고, 진짜 원인은 heading 속 보이지 않는 U+0008이었습니다.

**로컬 빌드는 하지 않습니다 (2026-08-31).** 빌드가 `<title>`/`<description>`/`<content:encoded>`를
전부 CDATA로 감싸므로 XML을 깨뜨릴 수 있는 벡터는 C0 제어문자 하나뿐이고, 그건 소스에서 잡힙니다.
빌드는 GitHub Actions가 합니다.

```bash
python3 "$VAULT/tools/rss_check.py" --source "markdown-blog/<목적지>/<파일명>.md"
```

- `status: "valid"` — 9단계로 진행합니다.
- `status: "invalid"` — **푸시를 차단합니다.** 출력의 codepoint 위치로 제어문자를 찾아 제거하고 다시 검사합니다.

> ⚠️ **`SkunkHtml.fs`·`SkunkUtils.fs`·`Program.fs`를 고쳤을 때는 반드시 로컬 빌드를 돌립니다.**
> 소스 스캔은 "현재 생성기가 CDATA를 쓴다"는 전제 위에 서 있어서, 생성기가 바뀌면 전제가 깨집니다.
> ```bash
> export PATH="$HOME/.dotnet:$PATH"
> cd "$VAULT" && dotnet run --project skunk-html.fsproj
> python3 tools/rss_check.py skunk-html-output
> rm -rf skunk-html-output   # 6.1GB — 확인 끝나면 지웁니다
> ```

### 9단계 — Git push

사용자 확인 후 `블로그/` 디렉토리에서:

```bash
git add <이동된 파일들>
git commit -m "post: <파일명에서 .md 제외한 제목>"
git push
```

커밋 메시지는 `post: ` 접두사로 통일합니다. 시리즈 글은 `post(series-name): ` 형식도 좋습니다 (예: `post(hinton): ...`).

**푸시 후 라이브 재확인(선택, 권장):** GitHub Actions 빌드 완료 후 라이브 피드를 캐시 우회로 받아 한 번 더 검증하면 "고쳐졌다"를 확정할 수 있습니다.

```bash
gh run watch --exit-status   # Actions 빌드·배포 완료까지 대기. 실패하면 0이 아닌 코드로 끝난다
curl -s "https://startedourmission.github.io/rss.xml?nocache=$(date +%s)" -o /tmp/live-rss.xml
python3 "$VAULT/tools/rss_check.py" /tmp/live-rss.xml
```

### 9.5단계 — Actions 결과 확인 (필수)

**푸시가 성공해도 배포는 실패할 수 있습니다.** 그때 사이트는 이전 버전을 계속 서비스하므로
겉으로는 멀쩡해 보이고 **갱신만 조용히 멈춥니다.** 이 볼트에서 크게 당한 사고가 전부 이 패턴이었습니다.

```bash
gh run watch --exit-status || echo "❌ Actions 배포 실패 — 사이트가 갱신되지 않았습니다"
```

실패하면 그 사실을 **완료 보고와 cron 로그 맨 위에 크게 남깁니다.** 조용히 넘어가지 않습니다.

### 10단계 — (삭제됨)

초안 원본이라는 게 따로 없으므로 지울 것도 없습니다. push 가 곧 게시입니다.

### 11단계 — 클리핑 아카이브

**게시한 글의 원본 클리핑이 `raw/Clippings/`에 있으면 무조건 `raw/Clippings/Archive/`로 이동합니다.** 제목·출처 URL이 일치하는 파일을 찾아 자동으로 처리합니다.

```bash
mv "$CLIPPINGS/<클리핑파일>.md" "$CLIPPINGS/Archive/"
```

이 단계는 사용자 확인 없이 자동으로 수행합니다. `Archive/` 폴더가 없으면 먼저 만듭니다.

### 12단계 — 완료 보고

게시된 파일 경로, 커밋 메시지, push 결과를 한눈에 보이게 출력합니다. 팩트체크 결과(✅/⚠️ 요약), 삭제된 드래프트, 아카이브된 클리핑이 있으면 함께 알립니다. GitHub Actions가 빌드하면 곧 사이트에 반영된다는 점도 알립니다.

## 예시

**사용자:** "SkillOrchestra 글 올려줘"

스킬은:
1. `markdown-blog/<목적지>/SkillOrchestra - Learning to Route Agents via Skill Transfer.md` 발견
2. `validate.py` 실행 — `status: "valid"` 확인, `date`가 오늘이 아니면 갱신 제안
3. 팩트체크 — arXiv 원문 대조로 "22.5%p 향상", "700배 학습 비용 절감", "위스콘신-매디슨·Salesforce" 확인. ❌ 없으면 통과, 있으면 차단·교정
4. `논문` 태그 → `markdown-blog/grid_Papers/`로 결정
5. 사용자 확인(팩트체크 요약 포함) 후 이동
6. 로컬 빌드 → `rss_check.py`로 생성된 피드 검증 (RSS 게이트 2), `valid` 확인
7. `git add → commit -m "post: SkillOrchestra - Learning to Route Agents via Skill Transfer" → push`

## 하면 안 되는 것

- **팩트체크에서 ❌(모순)가 나온 글을 그대로 게시하지 마세요.** 교정 후 재검증 통과 전까지 차단합니다.
- 팩트 교정을 핑계로 본문에 "이 수치는 불확실하다" 같은 의심 문장을 넣지 마세요 (STYLE.md 위반). 값만 고칩니다.
- 썸네일을 직접 생성하지 마세요. 항상 Codex 서브에이전트에 위임합니다.
- Headliner 태그를 임의로 추가하지 마세요. 사용자가 명시적으로 요청한 경우에만 — 유일한 상시 예외는 7.5단계의 이달의 인물 자동 교체입니다.
- **`ready`를 Claude가 `true`로 바꾸지 마세요.** 사용자 전용 결재 필드입니다. 게시하고 싶으면 체크박스를 켜는 게 아니라 이 스킬을 실행합니다.
- 게시본에 `ready` 필드를 남기지 마세요. 7단계에서 `ready_queue.py --strip`으로 제거합니다.
- 헤드리스에서 팩트체크 ❌가 난 글을 임의로 고쳐서 올리지 마세요. 건너뛰고 로그에 남깁니다.
- 사용자 확인 없이 프론트매터를 수정하지 마세요.
- `markdown-blog/` 루트에 새 글을 두지 마세요. 항상 하위 폴더로 갑니다.
- 다른 폴더의 이미지를 참조하는 글은 그대로 게시하지 마세요. 빌드에서 404 납니다.
- **RSS가 `invalid`인 채로 푸시하지 마세요.** 피드가 깨지면 전 구독자에게 조용히 영향이 가고, 원인(보이지 않는 제어문자)은 눈으로 못 찾습니다. `rss_check.py`가 짚은 위치로 역산해 고칩니다.
- RSS 오류를 소스만 보고 추측해서 "고쳤다"고 하지 마세요. 실제 생성된 피드를 `rss_check.py`로 재검증해 통과를 확인합니다.
- `--no-verify`로 hook을 우회하지 마세요. hook 실패는 원인을 찾아 해결합니다.
